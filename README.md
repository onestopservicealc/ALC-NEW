# ระบบเฝ้าระวังข่าวความรุนแรงและอุบัติเหตุจากแอลกอฮอล์

ระบบดึงข่าวไทยอัตโนมัติ คัดกรองเฉพาะเหตุที่เกี่ยวข้องกับเครื่องดื่มแอลกอฮอล์
สกัดเป็นโครงสร้างข้อมูล 49 ฟิลด์ด้วย AI แล้วส่งเข้าคิวให้เจ้าหน้าที่ตรวจสอบก่อนนับเป็นสถิติ

**Stack:** Vite + React 19 (SPA) · Vercel Functions · Supabase (Postgres + Auth + RLS) · Gemini

---

## ระบบทำงานอย่างไร

```
Vercel Cron (8 รอบ/วัน)                        Browser (React SPA)
        │                                              │
        ▼                                     anon key │ + RLS
  /api/cron/tick                                       ▼
  (งบเวลา 300 วินาที)                            Supabase Postgres
    A. ดึง RSS ทุกฟีด ──────┐                    ├─ sources      ทะเบียนฟีด
    B. คัดกรอง keyword ◄────┤                    ├─ articles     คิวข่าวดิบ
    C. AI คัดกรอง + สกัด    │                    ├─ incidents    49 ฟิลด์ + สถานะ
        │        service    │                    ├─ incident_revisions
        └─────── role key ──┘                    ├─ profiles     สิทธิ์ผู้ใช้
                 │                               ├─ ingest_runs  log การดึง
             Gemini API                          └─ incidents_public  VIEW ตัด PII → anon
```

**การอ่าน/เขียนข้อมูลปกติ** browser คุยกับ Supabase ตรงๆ โดยมี RLS เป็นตัวคุมสิทธิ์
**Vercel Functions** มีไว้เฉพาะงานที่ต้องถือ secret เท่านั้น (เรียก Gemini, ดึงข่าว, cron)

### สามด่านกรองก่อนข้อมูลเข้าสถิติ

| ด่าน | ทำอะไร | ค่าใช้จ่าย |
|---|---|---|
| 1. keyword | พจนานุกรมภาษาไทย ตัดข่าวที่ไม่เกี่ยวออกทันที | ฟรี — เป็นตัวคุมต้นทุน LLM หลัก |
| 2. AI screening | Gemini ตัดสินว่าแอลกอฮอล์เกี่ยวข้องกับการเกิดเหตุจริงไหม | 1 request ต่อข่าวที่ผ่านด่านแรก |
| 3. เจ้าหน้าที่ | ตรวจ 49 ฟิลด์ แก้ไข แล้วกดอนุมัติ | เวลาคน |

เฉพาะข่าวที่ผ่านครบสามด่านจึงจะขึ้นแดชบอร์ดสถิติ

## ติดตั้ง

### 1. Supabase

สร้างโปรเจกต์ (แนะนำ region Singapore) แล้วรัน migration ตามลำดับใน SQL Editor:

```
supabase/migrations/0001_init.sql          schema + RLS + view สาธารณะ
supabase/migrations/0002_seed_sources.sql  แหล่งข่าวเริ่มต้น 17 รายการ
supabase/migrations/0003_functions.sql     ฟังก์ชันหาข่าวซ้ำ + สรุปคิว
```

จากนั้นใน **Authentication → Providers** ให้ **ปิดการสมัครสมาชิกสาธารณะ** (Disable sign-ups)
แล้วเชิญผู้ใช้ทีละคนจาก **Authentication → Users → Invite**

ผู้ใช้ใหม่จะได้สิทธิ์ `viewer` โดยอัตโนมัติ เลื่อนขั้นด้วย SQL:

```sql
update public.profiles set role = 'admin'  where id = '<user-uuid>';
update public.profiles set role = 'editor' where id = '<user-uuid>';
```

| role | สิทธิ์ |
|---|---|
| `viewer` | ดูข้อมูลเต็มรวมชื่อบุคคล แต่แก้ไขไม่ได้ |
| `editor` | บันทึก แก้ไข อนุมัติ/ปฏิเสธ สั่งดึงข่าว |
| `admin` | ทุกอย่าง + จัดการแหล่งข่าว + ลบข้อมูล |

ผู้ที่ไม่ล็อกอินเห็นเฉพาะ view `incidents_public` ซึ่ง **ตัดชื่อผู้ก่อเหตุและชื่อเหยื่อออกทั้งหมด**
และแสดงเฉพาะเคสที่อนุมัติแล้ว

### 2. ตัวแปรสภาพแวดล้อม

คัดลอก `.env.example` เป็น `.env.local` (ตอนพัฒนา) หรือใส่ใน Vercel → Settings → Environment Variables

```bash
# ฝั่ง client — ถูกฝังลง bundle ตอน build (ปลอดภัยเพราะมี RLS คุม)
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=

# ฝั่ง server เท่านั้น — ห้ามขึ้นต้นด้วย VITE_ เด็ดขาด
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
GEMINI_API_KEY=
GEMINI_MODEL=gemini-flash-latest
CRON_SECRET=
```

> **สำคัญ:** `SUPABASE_SERVICE_ROLE_KEY` ข้าม RLS ได้ทั้งหมด ถ้าเผลอตั้งชื่อขึ้นต้นด้วย `VITE_`
> Vite จะฝังลงไฟล์ JavaScript ที่ทุกคนดาวน์โหลดได้

### 3. ตรวจก่อน deploy

```bash
npm install
npm run lint             # typecheck
npm run check:imports    # จำลองโหลดทุก endpoint ด้วยกติกา ESM ของ Node แบบเดียวกับ Vercel
npm run check:schema     # คอลัมน์ที่โค้ดขอ ต้องมีจริงใน migration + ชื่อบุคคลต้องไม่หลุดเข้า view สาธารณะ
npm run check:screening  # regression test ตัวคัดกรอง keyword (26 เคส)
npm run check:feeds      # ยิงฟีดจริงทุกตัว ดูว่ายังใช้ได้
npm run verify:gemini    # ยืนยัน model id + ความถูกต้องของการสกัด (ต้องมี GEMINI_API_KEY)
```

`verify:gemini` เทียบผลกับ fixture ที่รู้คำตอบอยู่แล้วใน `src/data/sampleNews.ts` เช่น
`alcohol_level=195`, `test_duration=20`, และกฎ `สังเกตุอาการ → alcohol_level ต้องเป็น null`

### 4. Deploy

```bash
vercel --prod
```

`vercel.json` ตั้งค่าไว้แล้ว: framework `vite`, output `dist`, `maxDuration: 300` สำหรับ `/api/**`

> ⚠️ **import ใน `api/` ต้องลงท้ายด้วย `.js` เสมอ** เช่น `from '../_lib/auth.js'`
> เพราะ `package.json` ตั้ง `"type": "module"` Node จึงบังคับให้ระบุนามสกุลใน ESM
> ถ้าลืม ตอนรันในเครื่องจะไม่พัง (Vite แปลงให้) แต่บน Vercel จะได้
> `ERR_MODULE_NOT_FOUND` แล้วฟังก์ชันตายตั้งแต่โหลดโมดูล คืน HTTP 500 ที่ไม่มีข้อความบอกอะไร
> — อาการนี้หลอกมาก เพราะดูเหมือนโค้ดในฟังก์ชันมีปัญหา ทั้งที่ยังไม่ได้เริ่มทำงานเลย

> ⚠️ ค่านี้ใน `vercel.json` **ไม่ชนะ** `export const config = { maxDuration: N }` ที่เขียนไว้ในไฟล์
> `@vercel/node` ส่งค่าจากในไฟล์เข้า Lambda โดยตรง ดังนั้นเพดานเวลาจริงของแต่ละ endpoint
> คือค่าที่เขียนไว้หัวไฟล์นั้นๆ ไม่ใช่ 300 — เช็คที่ไฟล์เสมอเวลาไล่ปัญหาเรื่องเวลา

### 5. รันในเครื่อง

```bash
npm run dev       # เฉพาะหน้าเว็บ (Vite) — /api จะยังไม่ทำงาน
npm run dev:api   # vercel dev — ได้ทั้งหน้าเว็บและ /api
```

## Cron: ตั้งเวลาที่ Supabase ไม่ใช่ Vercel

> ⚠️ **Vercel Cron ใน `vercel.json` ไม่เคยทำงานจริงในโปรเจกต์นี้**
> ตรวจฐานข้อมูลเมื่อ 2026-09-08 พบว่า `ingest_runs` ทั้งหมด 14 รอบเป็น `manual` ล้วน
> ไม่มี `cron` แม้แต่รอบเดียว และ Cron Jobs ไม่ปรากฏใน dashboard ของ Vercel เลย
> สาเหตุคือ `vercel.json` ประกาศไว้ 8 รายการซึ่งเกินโควตาของแพลนที่ใช้อยู่ Vercel จึงไม่ลงทะเบียนให้
> (เอกสารเดิมตรงนี้เขียนว่า Hobby ได้ถึง 100 รายการ ซึ่งไม่ตรงกับความจริงและทำให้เข้าใจผิดมานาน)

ระบบจึงย้ายไปตั้งเวลาที่ Supabase ด้วย `pg_cron` + `pg_net` ซึ่งไม่ขึ้นกับแพลนของ Vercel
ตั้งได้ถี่ถึงทุก 20 นาที และดูประวัติการรันได้ในฐานข้อมูลตัวเอง

```bash
npm run setup:cron -- https://ชื่อแอปของคุณ.vercel.app
```

สคริปต์อ่าน `CRON_SECRET` จาก `.env.local` แล้วสร้าง `pg-cron-setup.sql` (git มองข้ามไว้)
เอาไปวางใน **Supabase → SQL Editor → Run** ครั้งเดียวจบ

ตรวจว่าทำงานอยู่ไหม:

```sql
select start_time, status, return_message
from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'ingest-tick')
order by start_time desc limit 10;
```

หรือดูในหน้า **แหล่งข่าว** ของแอป ซึ่งเตือนเมื่อไม่มีการดึงสำเร็จเกิน 6 ชั่วโมง

- แต่ละ invocation มีงบเวลา 300 วินาที
- ถ้าย้ายไปแพลนที่รองรับ Vercel Cron ได้ครบ ค่อยเปิด `crons` ใน `vercel.json` กลับมาใช้แทนได้

pipeline ออกแบบให้หยุดกลางคันได้ทุกจุด สถานะทั้งหมดอยู่ใน DB รอบถัดไปจึงทำงานต่อจากเดิมได้เอง

## ขอบเขตข้อมูลที่ระบบเก็บ

ระบบเก็บเฉพาะข่าวที่เผยแพร่ **ตั้งแต่ 1 ม.ค. 2569 (2026-01-01)** เป็นต้นไป

ด่านกรองอยู่ในขั้นตอนบันทึกของ `api/_lib/ingest.ts` — ข่าวที่เก่ากว่านั้นถูกตัดทิ้ง
ตั้งแต่ก่อนเข้าฐานข้อมูล จึงไม่เปลืองโควตา AI และไม่ไปปนในสถิติ
จำนวนที่ตัดทิ้งแสดงในสรุปผลการดึงข่าวทุกรอบ

ข่าวที่ **ไม่มีวันเผยแพร่** ยังรับไว้ เพราะฟีดบางเจ้าไม่ส่งวันมาเลย และมักเป็นข่าวใหม่
ที่เพิ่งขึ้นเว็บ — ตัดทิ้งจะเสียของจริง

**ด่านที่สอง — วันเกิดเหตุ** ข่าวที่เผยแพร่วันนี้อาจรายงานเหตุการณ์เมื่อสองปีก่อน
(ข่าวศาลตัดสิน ข่าวติดตามคดี) ด่านวันเผยแพร่จับไม่ได้ จึงมีด่านแยกที่ `persistIncident`
ตัดเคสที่เกิดก่อนเกณฑ์ทิ้ง โดย**เติมวันจากวันเผยแพร่ให้ก่อนเสมอ** ถ้า AI สกัดวันไม่ได้ —
ตัดทันทีจะเสียข่าวใหม่ที่ยังใช้ได้

เปลี่ยนเกณฑ์ได้ด้วย env `INGEST_MIN_PUBLISHED_DATE` และ `INGEST_MIN_INCIDENT_DATE`
(รูปแบบ `YYYY-MM-DD`)

### บทเรียน: ข่าวจาก sitemap เคยทำให้ AI เดาปีผิด

ก.ย. 2569 พบเคสวันเกิดเหตุเป็นปี 2567 ทั้งที่เป็นข่าวใหม่ — ไม่ใช่ข่าวเก่าหลุดเข้ามา
แต่ **AI เดาปีเอง** เพราะข่าวจาก sitemap ถูกบันทึกด้วย `published_at: null` ตายตัว
โมเดลจึงไม่มีตัวอ้างอิงปี (ข่าวไทยมักเขียนแค่ "2 ก.ย." ไม่มีปี)

- กระทบเฉพาะแหล่ง sitemap **17 จาก 25 เคส (68%)** ส่วน RSS และ Google News ผิด **0%**
- แก้โดยให้ `sitemap.ts` อ่าน `<news:publication_date>` และ `<lastmod>` มาด้วย
  ซึ่งทั้งช่อง 7HD และ Thai PBS มีให้ครบ 100% อยู่แล้ว แต่โค้ดเดิมทิ้งไป
- ซ่อมข้อมูลเดิมด้วย `npm run repair:dates` (เติมวันจาก sitemap แล้วสั่งสกัดใหม่)

**ถ้าเจอวันเกิดเหตุแปลกๆ อีก ให้ตรวจก่อนว่าแถว `articles` มี `published_at` ไหม**

### ล้างข้อมูลเก่าที่ค้างอยู่

```bash
npm run data:cleanup                        # ดูว่าจะลบอะไรบ้าง ไม่แตะข้อมูล
npm run data:cleanup -- --yes               # ลบจริง สำรองเป็นไฟล์ให้ก่อนอัตโนมัติ
npm run data:cleanup -- --from 2027-01-01   # กำหนดวันตัดเอง
```

สคริปต์ทำสามอย่างที่ SQL ตรงๆ ทำไม่ได้

1. **กู้วันเกิดเหตุ** จาก `published_at` ของข่าวต้นทางก่อน — เคสที่ AI สกัดวันไม่ได้
   จะได้ไม่ถูกลบทิ้งทั้งที่ยังใช้ได้ (ครั้งที่รันจริงกู้ได้ 13 จาก 25 เคส)
2. **กันข่าวดิบที่เคสซึ่งเก็บไว้ยังอ้างอิงอยู่** ไม่ให้ถูกลบ ไม่งั้นเคสจะขาดที่มา
3. **ลบ incidents ผ่านผู้ใช้ระดับ admin ชั่วคราว** เพราะ service_role ถูกกันไม่ให้ลบตารางนี้
   โดยตั้งใจ (ดู `0008_sitemap_sources.sql`) แล้วลบบัญชีชั่วคราวทิ้งเสมอเมื่อจบ

## ดึงข่าวย้อนหลัง (backfill)

ระบบ cron ดึงเฉพาะข่าวใหม่ เพราะฟีด RSS เก็บแค่รายการล่าสุด 8-50 อัน (ครอบคลุม 1-3 วัน)
ถ้าต้องการข้อมูลย้อนหลัง ใช้สคริปต์ backfill ซึ่งอาศัยความสามารถ `?paged=N` ของฟีด WordPress

**แยกเป็น 2 ขั้นโดยตั้งใจ เพื่อให้คุมค่าใช้จ่ายได้:**

```bash
# ขั้นที่ 1 (ฟรี) — ดึงฟีดย้อนหลัง คัดกรอง keyword แล้วเก็บลงตาราง articles
npm run backfill -- --days 30 --dry-run    # ดูก่อนว่าจะได้อะไร ไม่แตะฐานข้อมูล
npm run backfill -- --days 30              # บันทึกจริง

# ขั้นที่ 2 (เสียเงิน) — ให้ AI สกัด 49 ฟิลด์ จากคิวที่ผ่านการคัดกรอง
npm run backfill:extract -- --status       # ดูสถานะคิวเฉยๆ
npm run backfill:extract -- --max 20       # ลองก่อน 20 ข่าว
npm run backfill:extract -- --max 200      # เดินหน้าเต็ม
```

ขั้นที่ 2 ใช้ pipeline ตัวเดียวกับ cron ทุกประการ ([ingest.ts](api/_lib/ingest.ts)) ผลลัพธ์จึงเหมือนกัน
และหยุดกลางคันได้ตลอด เพราะสถานะอยู่ในฐานข้อมูล

### สำนักข่าวไหนย้อนหลังได้บ้าง

ทดสอบจริงเมื่อ 2026-08-31 — ลองทั้ง `?paged=N`, `/page/N/feed/`, `?page=N` และ `?s=คำค้น&feed=rss2`

| สำนัก | ย้อนหลัง | เนื้อข่าวเต็มในฟีด | ความหนาแน่น |
|---|---|---|---|
| มติชน (อาชญากรรม) | ✓ ลึกถึง 3 เดือน+ | ✓ | ~5 วัน/หน้า |
| มติชน (ทั่วไป) | ✓ | ✓ | ~0.25 วัน/หน้า (ต้องไล่ ~118 หน้าต่อเดือน) |
| เดลินิวส์ (อาชญากรรม/ภูมิภาค) | ✓ | ✗ ต้อง fetch หน้าเว็บทีหลัง | ~0.75 วัน/หน้า |
| ประชาชาติ, ไทยโพสต์, INN | ✓ | ✓ | ต่างกันไป |
| **ข่าวสด, ไทยรัฐ** | **✗ ทำไม่ได้** | — | ได้เฉพาะข่าวล่าสุด |

ข่าวสดและไทยรัฐคืนหน้าเดิมทุกครั้งไม่ว่าจะใส่พารามิเตอร์แบบใด สคริปต์ตรวจจับเองด้วยการเทียบลิงก์
ระหว่างหน้า แล้วหยุดทันที (ไม่วนซ้ำไม่รู้จบ) — ช่องว่างนี้เติมได้บางส่วนด้วย Google News
ที่รองรับตัวกรองวันที่ เช่น `site:khaosod.co.th เมาแล้วขับ when:30d` ผลลัพธ์เป็นลิงก์ที่เข้ารหัสไว้
ซึ่งระบบถอดกลับเป็น URL ต้นทางให้เองได้แล้ว เจ้าหน้าที่จึงแค่กดยืนยัน (ดูหัวข้อ Google News ด้านล่าง)

### สิ่งที่ควรรู้ก่อนรัน

- ใช้เวลาหลายนาที เพราะจำกัดที่ 1 request/วินาที ต่อโดเมนตามมารยาท — ไล่ทุกสำนักพร้อมกัน
- เพดาน `--max-pages` เริ่มต้น 120 หน้า ถ้าชนเพดานก่อนย้อนถึงวันที่ขอ สคริปต์จะเตือนและบอกให้เพิ่มค่า
- อัตราข่าวที่เข้าเกณฑ์อยู่ราว **1%** ของข่าวทั้งหมด — ข่าวหลายพันชิ้นจะเหลือเข้า LLM ไม่กี่สิบ
  นี่คือเหตุผลที่ด่าน keyword สำคัญมากต่อการคุมต้นทุน

## ข้อจำกัดที่ต้องรู้

### Google News ซ่อน URL ต้นทาง (ถอดได้แล้ว แต่พึ่งพาไม่ได้ 100%)

Google เข้ารหัสลิงก์ในฟีดไว้ (`news.google.com/rss/articles/CBMi...`) การตาม redirect
การ base64 decode และการอ่าน HTML ของหน้า interstitial ล้วนไม่ได้ผล

แต่ **`batchexecute` ด้วย payload `garturlreq` รูปแบบปัจจุบันถอดได้** — ทดสอบเมื่อ 2026-09-07
ถอดสำเร็จ 8 จาก 8 ลิงก์ ใช้เวลาเฉลี่ย ~350 ms ต่อลิงก์ โค้ดอยู่ที่ `api/_lib/gnews.ts`

> ⚠️ นี่คือ endpoint ภายในที่ Google ไม่รับประกัน วันหนึ่งจะพังโดยไม่บอกล่วงหน้า
> รัน `npm run check:gnews` เป็นระยะเพื่อจับตอนที่มันพัง (สคริปต์ดึงลิงก์สดมาทดสอบจริง
> และคืน exit code ไม่ใช่ 0 เมื่อถอดสำเร็จต่ำกว่า 70%)

ระบบจึงใช้กลยุทธ์ 2 ชั้น:

- **RSS สำนักข่าวโดยตรง** = เชื้อเพลิงหลัก ได้ URL จริงและเนื้อข่าวเต็ม สกัด 49 ฟิลด์อัตโนมัติได้ครบ
- **Google News** = ตัวจับสัญญาณ เก็บพาดหัว + ชื่อสำนัก + ลิงก์ Google News ไว้เป็น "lead"
  เจ้าหน้าที่กดปุ่ม **ยืนยันข่าวนี้** ครั้งเดียวจบ ไม่ต้องเปิดข่าวไปคัดลอก URL —
  เซิร์ฟเวอร์ถอดลิงก์ให้เองแล้วสกัดต่อ (แท็บ **คิวตรวจสอบข่าว → ต้องยืนยันลิงก์**)
  ถ้าถอดไม่สำเร็จ หน้าจอจะเปิดช่องให้วาง URL เองเป็นทางถอย งานจึงไม่ตัน

lead ถูกคุมปริมาณด้วยการกันข่าวซ้ำ (ข่าวเด่นหนึ่งเรื่องโผล่พร้อมกัน 5-10 สำนัก)
และโควตา `INGEST_MAX_LEADS_PER_TICK` (ค่าเริ่มต้น 15 ต่อรอบ)

สำนักข่าวที่โผล่ใน lead บ่อยๆ คือสัญญาณว่าควรเพิ่มฟีดของสำนักนั้นในหน้า **แหล่งข่าว**

### Gemini API เรียกไม่ได้ (403 / 404 / 429)

`GEMINI_MODEL` ต้องเป็นรุ่นที่ **บัญชีของคุณเรียกได้จริง** ซึ่งไม่ตรงกับรายการในหน้าเอกสารเสมอไป
ใช้คำสั่งนี้หาว่ารุ่นไหนใช้ได้ — มันยิง `generateContent` จริงทีละรุ่น ไม่ได้ดูแค่ `models.list`
(ซึ่งเชื่อไม่ได้ เพราะบางรุ่นอยู่ในลิสต์แต่เรียกจริงแล้ว 404):

```bash
npm run verify:gemini -- --probe
```

อ่านผลตามรูปแบบ error:

| error | ความหมาย | ทำอย่างไร |
|---|---|---|
| `404 NOT_FOUND` — *no longer available to new users* | รุ่นนั้นปิดรับผู้ใช้ใหม่แล้ว | เลือกรุ่นอื่นที่ probe บอกว่า ✓ |
| `429 RESOURCE_EXHAUSTED` | โควตาของรุ่นนั้นเป็น 0 สำหรับบัญชีนี้ | ใช้รุ่น Flash แทน Pro หรือเปิด billing |
| `403 PERMISSION_DENIED` — *Your project has been denied access* | **บัญชี/โปรเจกต์ถูกบล็อก** ไม่เกี่ยวกับชื่อโมเดล | ดูด้านล่าง |

ถ้าได้ `403 PERMISSION_DENIED` เหมือนกันทุกรุ่น แปลว่าปัญหาอยู่ที่บัญชี ไม่ใช่โค้ด — เรียงตามที่พบบ่อย:

1. **บัญชี Google Workspace ขององค์กรปิดกั้นไว้** — โดเมนอย่าง `@*.go.th` ผู้ดูแลระบบมักปิด
   AI Studio / Generative Language API ไว้ **ทดสอบเร็วที่สุดคือสร้างคีย์ด้วย Gmail ส่วนตัวแล้วลองใหม่**
2. **คีย์ไม่ได้ผูกกับ Google Cloud project จริง** — คีย์ปกติขึ้นต้นด้วย `AIzaSy` ยาว 39 ตัว
   ถ้าคีย์ของคุณขึ้นต้นด้วยอย่างอื่น (เช่น `AQ.`) ให้สร้างใหม่ผ่าน Google Cloud Console
   โดยเปิดใช้ **Generative Language API** ในโปรเจกต์นั้นก่อน
3. **ประเทศ/ภูมิภาคยังไม่รองรับโควตาฟรี** — ต้องเปิด billing

**ทางที่เหมาะกับงานหน่วยงานราชการมากกว่า: ใช้ Vertex AI** — โมเดล Gemini ชุดเดียวกัน
แต่ยืนยันตัวตนด้วย service account ภายใต้โปรเจกต์ GCP ขององค์กรเอง ควบคุมได้ว่าข้อมูลอยู่ภูมิภาคไหน
ไม่ถูกนำไปเทรน และคุมค่าใช้จ่ายผ่านระบบขององค์กร — SDK `@google/genai` ที่ใช้อยู่รองรับโหมดนี้อยู่แล้ว
แก้เฉพาะการสร้าง client ใน [api/_lib/gemini.ts](api/_lib/gemini.ts) เป็น `{ vertexai: true, project, location }`

### URL ฟีดตายบ่อย

ตอนสำรวจครั้งแรกพบว่าใช้ไม่ได้ **8 จาก 20 ฟีด** ที่ลอง (ThaiPBS, MGR, PPTV, สนุก, คมชัดลึก,
NationTV, SpringNews, Amarin) รายการฟีดจึงเก็บเป็น**ข้อมูลในตาราง `sources`** ไม่ใช่ hardcode
และมี `npm run check:feeds` ไว้ตรวจซ้ำเป็นระยะ — ฟีดที่ error ติดกัน ≥3 ครั้งจะขึ้นเตือนในหน้าแหล่งข่าว

ฟีดที่ยืนยันแล้วว่าใช้ได้ (2026-08-30): ข่าวสด, มติชน (มีหมวดอาชญากรรมแยก), เดลินิวส์,
ไทยรัฐ, ประชาชาติ, ไทยโพสต์, INN — เจ็ดในสิบฟีดส่ง `content:encoded` ที่มีเนื้อข่าวเต็ม
(~9,000 ตัวอักษร) มาให้เลย จึงไม่ต้อง scrape หน้าเว็บ

### การคัดกรองภาษาไทย

ภาษาไทยไม่เว้นวรรคระหว่างคำ การจับ substring จึงชนคำอื่นได้ง่าย — `"สุรา"` อยู่ใน `"สุราษฎร์ธานี"`,
`"ชน"` อยู่ใน `"ประชาชน"` `"ชนบท"` `"ชนะ"` `"ชนิด"`, `"เมา"` อยู่ใน `"เมาส์"`
พจนานุกรมใน `api/_lib/screen.ts` จึงใช้วลียาวเป็นหลัก และใช้ regex ที่มี lookaround
สำหรับคำสั้นที่เลี่ยงไม่ได้

**แก้พจนานุกรมเมื่อไหร่ ให้รัน `npm run check:screening` ทุกครั้ง** — ชุดทดสอบ 26 เคสนี้
มาจากกรณีที่เคยผิดจริงตอนทดสอบกับฟีดจริง

## ความเป็นส่วนตัวและลิขสิทธิ์

- **ชื่อบุคคลไม่เผยแพร่สาธารณะ** — view `incidents_public` ตัด `perpetrator_name` และ
  `victim_1..3_name` ออก ผู้ไม่ล็อกอินไม่มีสิทธิ์แตะตาราง `incidents` เลย
- **ไม่เก็บเนื้อข่าวต้นฉบับ** — `full_text` ถูกลบทิ้งทันทีหลังสกัดเสร็จ เก็บไว้เพียง URL
  และสรุปที่ระบบเขียนเอง
- **อ้างอิงแหล่งที่มาเสมอ** — `url` และ `news_agency` เป็นฟิลด์ Not Null ตามสเปก
- **ดึงข้อมูลอย่างสุภาพ** — จำกัด 1 request/วินาที ต่อโดเมน และส่ง User-Agent ที่ติดต่อกลับได้
  (ตั้งค่าผ่าน `INGEST_USER_AGENT`)
- ตัวเลขในแดชบอร์ดเป็น**สถิติจากข่าวที่ถูกรายงาน** ไม่ใช่จำนวนเหตุการณ์ที่เกิดขึ้นจริงทั้งหมด
